# Вебхук программы лояльности Rivo

Код: `bot/webhooks.py` (транспорт, подпись, сэмплер, сторож),
`core/adapters/rivo/parse.py` (разбор тела), `core/usecases/loyalty.py`
(кому и что написать). Здесь — то, чего из кода не восстановить: что настроено
руками вне репозитория, как Rivo ведёт себя на самом деле и чем это отличается
от его документации, и как всё это проверять и менять.

Состояние на 2026-09-16: **канал работает.** С 14:34 UTC идут настоящие события,
подпись проходит, тела разбираются.

## Зачем

Программа лояльности живёт в Rivo на стороне сайта: баллы, уровни, рефералы.
Бот не делает ничего из этого и не должен. Он умеет одно, чего не умеет сайт:
написать первым. Rivo присылает событие — бот через минуту сообщает человеку в
Telegram. Если цифры разойдутся, прав Rivo.

## Путь запроса

```
Rivo (rest-client, Ruby, AWS)
  → https://ksanalytics.duckdns.org/rivo/<секретный сегмент>
  → keycrm-nginx     (проект key-api-bot: у него 80/443 и сертификат)
  → ks-tg-bot:8081   (порт не опубликован, только сеть key-api-bot_default)
```

**Nginx — в git соседнего проекта**, `halloweex/key-api-bot`,
`nginx/nginx.conf`, PR #198 от 16.09. Блок `location ^~ /rivo/` **префиксный и
без секрета**: репозиторий публичный. Секретный путь проверяет сам бот — чужой
путь под `/rivo/` получает его `404: Not Found`. Upstream задан переменной
(`set $bot_upstream ks-tg-bot`), как всё в том файле: литеральное имя
резолвится один раз при старте, и 23.08 это роняло их сервис.

**Ловушка, которая стоила трёх потерь маршрута.** `nginx.conf` смонтирован в
контейнер как файл, bind-mount файла привязан к inode, а их деплой делает
`git reset --hard` — git заменяет файл целиком, у него новый inode. Сам по себе
деплой nginx **не пересоздаёт** (compose пересоздаёт только сервисы со
сменившимся образом или конфигом — 16.09 в 06:47 это случилось, видимо, из-за
нового образа `nginx:alpine`, а в 12:24 нет), и тогда контейнер продолжает
читать старый файл. Поэтому после **любой** правки `nginx.conf` в key-api-bot,
уже после их зелёного деплоя:

```
cd /opt/key-api-bot && docker compose up -d --force-recreate nginx
```

Проверять, что применилось, по работающему конфигу, а не по файлу:
`docker exec keycrm-nginx nginx -T | grep '\^~ /rivo/'`. `nginx -s reload`
помогает, только если inode в контейнере и на диске совпадают
(`stat -c %i` там и там); пока контейнер держит старый inode, reload
перечитывает старый файл.

**В `docker-compose.yml` бота** он подключён ко второй сети
`key-api-bot_default`, иначе nginx его не видит. Ничего не публикуется.

## Что в `/opt/ks-tg-bot/.env`

Без обеих переменных не поднимается ни эндпоинт, ни сторож — они в одном `if`
в `bot/__main__.py`.

- **`RIVO_WEBHOOK_SECRET`** — ключ подписи. **Один на весь аккаунт Rivo**: в
  кабинете внизу страницы Webhooks — «Your webhooks will be signed with …».
  Документация Rivo намекает на ключ у каждого вебхука; кабинет говорит иначе.
  Можно несколько через запятую — это для смены ключа без перерыва (новый рядом
  со старым, пока Rivo не переключится). Пустые элементы отбрасываются: HMAC с
  пустым ключом посчитает кто угодно.
- **`RIVO_WEBHOOK_PATH`** — секретный путь, `/rivo/<32 hex>`. Тоже можно
  несколько через запятую — для смены пути без потерь (см. ниже). Маршрутом
  становятся только записи, начинающиеся с `/rivo/`, без символов шаблона
  (`{}?#%`, кавычки, пробел) и без `/` в конце; дубли схлопываются.

При старте бот пишет, сколько прочитал ключей и путей, никогда — какие:
`Rivo webhook accepts N signing key(s)`, `Rivo webhook serves N path(s)`.

Узнать путь, не выводя его в чужие места:
`grep '^RIVO_WEBHOOK_PATH=' /opt/ks-tg-bot/.env` — прямо в терминале на сервере.

## Кабинет Rivo

Shopify admin → Apps → Rivo Loyalty → Settings → **Webhooks**, или прямо:
`https://shopify.com/admin/apps/rivo-loyalty/merchant_webhooks`. По справке
Rivo это часть Developer Toolkit (тариф Plus); у магазина страница открывается.

- **Create webhook**: Event Type, URL, Description. Один вебхук на тип события.
- **Перевыпуска ключа в кабинете нет.** Только через поддержку Rivo.
- **Test → Send Test Webhook** шлёт пробное событие этого типа. **Пометки
  «тест» в теле нет**, и обрабатывается оно как настоящее. Пока бот понимает
  тип, Test может написать живому подписчику, если пример клиента у Rivo с ним
  совпадёт. Нажимать осознанно.

**Корень всей истории до 16.09:** на странице Webhooks **не было ни одного
вебхука**. Rivo не звонил ни разу, потому что звонить было некому.

Бот понимает события:

| Событие Rivo | Кому | Что получит |
|---|---|---|
| `balance_transaction/created` | `customer` | «Тобі нараховано N балів», с балансом |
| `points_event/created` | `customer` | то же |
| `customer_vip_tier/upgraded` | `customer` | поздравление с новым уровнем |
| `notification/points_expiry_warning` | `customer` | «бали скоро згорять», с балансом |
| `notification/points_expiry_last_chance` | `customer` | то же |
| `notification/credits_expiry_warning` | `customer` | то же |
| `notification/credits_expiry_last_chance` | `customer` | то же |
| `referral/completed` | **`referrer_customer`** | «подруга зробила замовлення» |

В кабинете заведены: `balance_transaction/created`, `points_event/created`,
`customer_vip_tier/upgraded`, `notification/points_expiry_warning`,
`referral/completed`. Три оставшихся бот понимает, но вебхуков на них нет —
завести, если нужны. Тексты — в `core/texts.py`, с учётом рода обращения
(`docs/gender.md`).

**Настоящие начисления приходят как `balance_transaction/created`** — восемь
штук за первые два часа. С `points_event/created` за то же время не пришло
ничего. Списание баллов не сообщается: `points_diff` со знаком, отрицательное не
объявляется.

**Реферал адресуется пригласившей и никогда подруге.** В настоящем теле нет
`customer`, есть `referrer_customer` и `referred_customer`. Если бот знает
только подругу, не пишет никто.

## Как Rivo подписывает на самом деле

**Документация Rivo** описывает заголовок `rivo-signature` = base64 HMAC-SHA256
сырого тела. **Так Rivo не шлёт.** Измерено 16.09 по его же запросам:

- заголовки `rivo-webhook-signature`, `rivo-webhook-id`,
  `rivo-webhook-timestamp`, `rivo-webhook-topic`, `rivo-webhook-api-version` —
  схема Standard Webhooks;
- подпись = base64 HMAC-SHA256 по строке **`id.timestamp.тело`**, ключ — текст
  из кабинета как есть;
- **тип события — в заголовке `rivo-webhook-topic`**, в теле `event_type` нет.

Найдено так: пока схема была неизвестна, бот перебирал правдоподобные варианты и
писал в лог, какой совпал. Восемь пробных и восемь настоящих запросов совпали с
одним — остальные варианты удалены. Документированный `rivo-signature` бот
по-прежнему принимает: это публичный контракт Rivo, на нём может говорить старая
версия API. Если тело само называет `event_type`, оно главнее заголовка.

Возраст `timestamp` **не проверяется**: неизвестно, переподписывает ли Rivo
повторную доставку новым временем, а окно, отвергающее его собственные повторы,
теряло бы уведомления.

## Когда что-то не так: что смотреть

**Лог бота** — `docker logs ks-tg-bot 2>&1 | grep -i rivo`:

| Строка | Значит |
|---|---|
| `verified (rivo-webhook-signature, path #1/1, key #1/1), topic …` | принято; номера пути и ключа — чтобы при смене видеть, куда и чем шлёт Rivo |
| `refused …: no signature header; …headers sent: …` | заголовка подписи нет — список имён заголовков скажет, что пришло вместо |
| `refused …: signature did not match; signature shape: …` | подпись есть, не сошлась — ключ не тот или схема сменилась; форма (длина, метка `v1,`) без значения |
| `Kept a redacted Rivo sample at …` | тело не удалось прочитать целиком — образец на диске, админам пришёл 🧪 |

**Ответ бота в логе nginx** — `docker logs keycrm-nginx 2>&1 | grep '"POST /rivo/'`:
размер ответа `2` байта = `ok` (разобрано и передано дальше), `7` = `ignored`.

**Сэмплер.** Тело, которое бот не смог прочитать целиком (неизвестный тип,
баллы без `points_diff`, известный тип без адресата), пишется в
`/app/data/rivo-samples/<тип>.json` (`/` в типе заменяется на `_`, без типа —
`unknown.json`), по одному на тип, без перезаписи, **не больше 30 файлов** —
дальше новые не пишутся, и об этом ничего не сообщается.
**Обезличивание сквозное**: `customer` пересобирается, всё остальное проходит
насквозь — текст заменяется длиной (`<str:16>`), кроме перечислений
(`event_type`, `source`, `status`…) и моментов (`*_at`). Проба берётся только
после проверки подписи. Перед тем как класть образец фикстурой в публичный
репозиторий, заменять внутренние id Rivo и id магазина выдуманными.

Фикстуры с тел, которые прислал сам Rivo, — **пробных**, из кнопки Test:
`tests/fixtures/rivo/points_event_created.json` (начисление; тип в имени условный,
тело пришло без `event_type`) и `tests/fixtures/rivo/referral_completed.json`.
Тела настоящего `balance_transaction/created` в фикстурах нет: восемь настоящих
разобрались целиком, и сэмплер их не сохранял.

**`405` не значит «маршрута нет».** Наш бот сам отвечает `405 post only` на всё,
кроме POST, по верному пути. `{"detail": …}` — это уже FastAPI соседей, то есть
запрос до бота не дошёл.

**Любая проверка курлом или браузером — это «приход».** Отметка ставится до
проверки подписи, чтобы видеть «путь из интернета достаёт до процесса». Цена:
проверка отодвигает алерт тишины на трое суток. Отличать по `meta` строки в
`events`: `agent` (обрезан до 32 символов) — `curl/…`, `Mozilla…`,
`TelegramBot…` против `rest-client/2.1.0 (linux x86_64)` у Rivo. На `from_lan` не смотреть: проба с сервера тоже
идёт через публичный адрес.

## Сторож тишины

Нет приходов трое суток — админам алерт, повтор раз в семь суток, пока не
позвонят. Считает от более позднего из двух: последнего прихода и момента,
когда бот начал следить. Оба момента и момент последнего алерта лежат в
`events` (`rivo_webhook_arrived`, `rivo_watch_started`, `rivo_silence_alerted`),
а не в процессе — деплой их не сбрасывает. Перевзвести сторожа перезапуском
нельзя, это запись в базу. Посмотреть:

```
docker exec ks-tg-bot python -c "
import sqlite3; c=sqlite3.connect('file:/app/data/bot_data.db?mode=ro', uri=True)
print(list(c.execute(\"select event, max(created_at), count(*) from events \"
                     \"where event like 'rivo_%' group by event\")))"
```

## Смена пути без потерь

Путь меняется в двух местах — в `.env` и в URL каждого вебхука в кабинете, —
а кабинет правится руками. Поэтому на время правки бот слушает оба пути.
Все команды — на сервере, путь нигде не печатается и в браузере не открывается:
прошлый утёк именно так.

**0. Предусловие.** В проде работает сборка, которая понимает несколько путей:
`docker logs ks-tg-bot 2>&1 | grep 'serves .* path(s)'` что-то показывает, и
`grep '^IMAGE_TAG=' /opt/ks-tg-bot/.env` совпадает с
`docker inspect -f '{{.Config.Image}}' ks-tg-bot`. Старая сборка сочла бы
`/rivo/a,/rivo/b` одним путём, и **оба** ответили бы `404`. По той же причине
**образ не откатывать, пока в `.env` два пути**: сначала оставить один — тот, на
который сейчас шлёт Rivo. Во время смены не пушить в master ничего, кроме `.md`:
каждый деплой — ещё один перезапуск бота.

1. Копия `.env` в `/root` с правами 600. Новый путь сгенерировать
   (`secrets.token_hex(16)`) и **дописать перед** текущим значением, а не
   перепечатывать старый руками: `RIVO_WEBHOOK_PATH=/rivo/<новый>,/rivo/<старый>`.
   Nginx не трогать — блок префиксный.
2. `cd /opt/ks-tg-bot && docker compose up -d --force-recreate bot`
   (именно так: `restart` не перечитывает `env_file`). Проверить **все три**:
   `docker compose ps bot` — Up, а не Restarting; в логе `serves 2 path(s)` и
   `Webhook endpoint listening on :8081`; оба пути отвечают `405 post only` на
   GET с сервера (путь подставлять из `.env`). Если что-то не так — вернуть копию
   `.env` и пересоздать.
3. В кабинете Rivo поменять URL во **всех** вебхуках на новый. Сверить число
   вебхуков с числом исправленных.
4. Подождать, пока на новый путь придут настоящие события, а на старый — ни
   одного POST, хотя бы несколько часов: в логе бота `path #1/2` у каждого
   `verified`, и
   `docker logs keycrm-nginx --since <время шага 3> 2>&1 | grep -cF "\"POST $OLD"`
   даёт `0` (`OLD` подставить из `.env`).
5. Убрать старый путь, пересоздать бота: `serves 1 path(s)`. С сервера: старый
   путь — `404: Not Found`, новый — `405 post only`.

Проверки GET-запросом — тоже «приходы» и отодвигают алерт тишины; переключение
Rivo смотреть по строкам `verified`, а не по приходам.

Ключ меняется так же: новый через запятую рядом со старым; убрать старый, когда
в `verified` будет `key #1/2`.

## Чего механизм не делает

**Не показывает баллы по запросу** и не выдаёт личную реферальную ссылку: это
REST API Rivo, Developer Toolkit, тариф Plus.

**Не находит тех, кого не знает.** Rivo знает людей по email, бот по чату,
связывает их `users.email` из карточки KeyCRM. На 16.09 email есть у 5
пользователей бота из 16, а покупателей в программе тысячи — поэтому из
первых восьми настоящих начислений сообщения не получил никто, и это норма.

## Открыто

- **Ключ подписи скомпрометирован.** Целиком — на скриншотах в переписке 25.08 и
  16.09; первая половина — тестовая константа в истории публичного
  репозитория halloweex/ks-tg-bot. Перевыпуск — через поддержку Rivo.
- **Путь засветился** в Telegram 16.09 (его открыл бот предпросмотра ссылок).
  Смена — процедура выше.
- **Живой подписчик ещё не получал сообщения** от настоящего события: цепочка
  проверена до `announce`, дальше — тестами.
- **Нет защиты от повтора.** Заголовок `rivo-webhook-topic` не подписан, возраст
  `timestamp` не проверяется, повтор `rivo-webhook-id` не отбрасывается. Кто
  перехватит один подписанный запрос, может отправить его ещё раз с другим
  топиком. Пока ключ скомпрометирован, это вторично — подделать можно и без
  перехвата; после перевыпуска ключа стоит хранить обработанные id.
