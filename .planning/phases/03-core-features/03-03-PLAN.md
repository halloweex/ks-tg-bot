2. Create `bot/handlers/info.py` with a Router and these callback query handlers:

   a) `show_about` — `InfoAction.filter(F.page == "about")`. `await callback.answer()` first, then `callback.message.edit_text(config.about_text, reply_markup=_back_to_info_kb())`.

   b) `show_contacts` — `InfoAction.filter(F.page == "contacts")`. Same pattern with `config.contacts_text`.

   c) `show_payment` — `InfoAction.filter(F.page == "payment")`. Same pattern with `config.payment_text`.

   d) `show_delivery` — `InfoAction.filter(F.page == "delivery")`. Same pattern with `config.delivery_text`.

   Each handler needs `config: AppConfig` as a DI parameter.

   Helper function `_back_to_info_kb() -> InlineKeyboardMarkup`: builds a single-button keyboard with `InfoAction(page="back")` and text `BTN_BACK`. This returns to the info submenu (not main menu).

   Wrap all `edit_text` calls in try/except for `TelegramBadRequest` — if caught, send a new message instead.

3. Create `bot/handlers/support.py` with a Router and these handlers:

   a) `enter_support_mode` — callback handler for `MenuAction.filter(F.action == "support")`:
      - `await callback.answer()` first.
      - Set FSM state: `await state.set_state(SupportStates.waiting_message)`.
      - `callback.message.edit_text(texts.MSG_SUPPORT_PROMPT)` — no keyboard (user types freely).
      - DI params: `callback: CallbackQuery`, `callback_data: MenuAction`, `state: FSMContext`.

   b) `forward_to_support` — message handler for `SupportStates.waiting_message`:
      - Send a metadata line to admin FIRST: `await bot.send_message(chat_id=config.support_chat_id, text=texts.MSG_SUPPORT_ADMIN_NOTE.format(chat_id=message.chat.id))`.
      - Then forward the actual message: `await bot.forward_message(chat_id=config.support_chat_id, from_chat_id=message.chat.id, message_id=message.message_id)`.
      - Then send instruction to admin: `await bot.send_message(chat_id=config.support_chat_id, text=texts.MSG_SUPPORT_REPLY_INSTRUCTION)`.
      - Confirm to user: `await message.answer(texts.MSG_SUPPORT_FORWARDED, reply_markup=main_menu_kb(config.website_url))`.
      - Clear FSM state: `await state.clear()`.
      - DI params: `message: Message`, `state: FSMContext`, `bot: Bot`, `config: AppConfig`.
      - NOTE: Using the metadata message pattern (not forward_from) per research Pitfall 2 — forward_from is None when user has privacy enabled. The chat_id in the metadata line is the reliable way to route replies.

   c) `admin_reply` — message handler that fires when the admin (support person) replies to a forwarded message:
      - Filter: `F.chat.id == config.support_chat_id` AND `F.reply_to_message` must be present.
      - IMPORTANT: Cannot use `config.support_chat_id` directly in the filter decorator because config is a runtime value. Instead, use a custom filter or check inside the handler body.
      - Implementation approach: Register the handler on the router with only `F.reply_to_message` filter. Inside the handler, check `if message.chat.id != config.support_chat_id: return` (ignore non-admin messages that have reply_to).
      - Actually, better approach: since this handler should ONLY fire for admin chat, we need a way to scope it. Use a filter function:
        ```python
        @router.message(F.reply_to_message)
        async def admin_reply(message: Message, bot: Bot, config: AppConfig) -> None:
            if message.chat.id != config.support_chat_id:
                return  # Not admin, ignore
        ```
      - Extract user chat_id from the metadata message. The admin replies to the forwarded message, but we need the chat_id from the metadata message that precedes it. Strategy:
        - Look at `message.reply_to_message` — this is what the admin replied to.
        - Check if the replied-to message has `forward_from` — if so, use `forward_from.id`.
        - If `forward_from` is None (privacy), look at the message BEFORE the replied-to message. But this is unreliable.
        - SIMPLER APPROACH: Parse the chat_id from the metadata message. But admin may reply to the forwarded message, not the metadata line.
        - BEST APPROACH for v1: Store a mapping. When forwarding, store `{forwarded_message_id_in_admin_chat: user_chat_id}` in FSM data or a simple dict. But FSM is per-user, not per-admin.
        - PRAGMATIC v1 APPROACH: Use `forward_from` when available. When not available, look at the text of the message the admin is replying to — if it matches the metadata format `MSG_SUPPORT_ADMIN_NOTE`, parse the chat_id from it. Also check the message above (previous message from bot to admin).
        - SIMPLEST RELIABLE APPROACH: When the admin replies to ANY message from the bot, check if the replied-to message text starts with the metadata prefix and extract chat_id. If the admin replies to the forwarded message itself, try `forward_from.id`. If neither works, send `MSG_SUPPORT_NO_REPLY_TARGET`.

        Implementation:
        ```python
        replied = message.reply_to_message
        user_chat_id = None

        # Try 1: forward_from (works if user hasn't enabled privacy)
        if replied and replied.forward_from:
            user_chat_id = replied.forward_from.id

        # Try 2: metadata message (parse chat_id from "chat_id: 12345")
        if not user_chat_id and replied and replied.text:
            import re
            match = re.search(r"chat_id:\s*(\d+)", replied.text)
            if match:
                user_chat_id = int(match.group(1))

        if not user_chat_id:
            await message.answer(texts.MSG_SUPPORT_NO_REPLY_TARGET)
            return

        # Send admin's reply to user
        await bot.send_message(chat_id=user_chat_id, text=f"{texts.MSG_SUPPORT_REPLY_PREFIX}\n\n{message.text}")
        ```
      - DI params: `message: Message`, `bot: Bot`, `config: AppConfig`.
