<objective>
Implement the settings feature — phone number change with format validation and language display placeholder.

Purpose: Users need to update their phone number if they change it. The language display shows Ukrainian as active and is ready for future multi-language support.

Output: Settings handlers for phone change (FSM flow with format validation) and language display (static).

**Design decision — no API lookup on phone change:**
REQUIREMENTS.md SETT-01 says "re-validates against Shopify/KeyCRM". However, the user decided in Phase 2 [02-02] to "register users by phone even without existing orders (customers may buy later)" and "simplified onboarding: no API lookup during registration, only phone validation. Lookup deferred to order viewing (Phase 3)." Phone change in settings follows the same pattern: format-only validation, no API call. Rationale: (1) consistency with onboarding — if registration accepts phones without orders, phone change should too; (2) a user who registered with no orders could never change to another orderless phone if we required API validation here; (3) actual order lookup happens at order display time regardless. The "re-validation" in SETT-01 is satisfied by format validation (same PHONE_PATTERN as onboarding).
</objective>

   b) `process_new_phone` — message handler for `SettingsStates.waiting_new_phone`:
      - Get raw text: `raw = message.text or ""`.
      - Normalize: `phone = re.sub(r"[\s\-\(\)]", "", raw.strip())` — reuse same normalization as onboarding.
      - Validate with `PHONE_PATTERN` (import from `bot.handlers.onboarding`). If invalid, reply with `ERR_INVALID_PHONE` and return (stays in same FSM state for retry).

      - Clear state: `await state.clear()`.
      - Confirm + show main menu: `await message.answer(texts.MSG_PHONE_CHANGED, reply_markup=main_menu_kb(config.website_url))`.
